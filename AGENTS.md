# Инструкции агента Yantages

## Назначение
Разрабатываем «Орбиту»: 3D-игру про межпланетного курьера и его корабль-дом.
Общение и документация — по-русски, имена кода — по-английски.
Основной движок по решению пользователя — Unity. Предыдущие прототипы не развивать без отдельной задачи.

## Перед работой
Прочитать docs/README.md, docs/STATUS.md и относящиеся к задаче документы.
Проверить git status, локальные инструкции и затрагиваемый код. Не включать чужие или случайные файлы в коммит.
Выбирать небольшую законченную задачу с наблюдаемым результатом. Не подменять запрос планированием.
Авторитет: прямое указание пользователя, затем актуальный код и проверка, затем документация.
Не выдавать идею за принятое решение, существующий код — за проверенную реализацию.

## Проектные навыки
Навыки хранятся в .agents/skills/ и версионируются с проектом. Если они не появились в каталоге среды, читать SKILL.md напрямую.
- orbita-unity: изменение Unity-кода и сцен.
- orbita-narrative: сценарий, заказы, диалоги, игровые идеи.
- orbita-verification: проверка запуска, взаимодействий и сборки.
Читать только подходящие навыки. Системные навыки использовать при необходимости; проектные инструкции не расширяют разрешения.

## Реализация
Unity-проект — unity/. Точную версию редактора закрепить после первого успешного импорта; не придумывать ProjectVersion.txt.
Новые Unity-ассеты хранить вместе с их .meta; существующие GUID сохранять. Не коммитить Library, Temp, секреты и сборки.
Текущий CourierShip.cs — временный монолит. При существенном расширении отделять построение сцены, движение, взаимодействия и состояние заказа по необходимости, без переписывания всего проекта ради структуры.
Не добавлять платные ассеты, сервисы, пакеты и альтернативные движки без потребности задачи.
Визуальные решения сверять с docs/ART_DIRECTION.md; любые внешние ресурсы проверять на право использования.

## Проверка и завершение
Следовать docs/WORKFLOW.md и docs/TESTING.md. Не сообщать «работает», если был проверен только текст кода.
Обновлять STATUS и связанные документы при изменении фактов, управления, сценария или состояния задачи.
Перед коммитом изучить diff и git diff --check; запускать проверки соразмерно изменению.
Пользователь разрешил коммиты и push в связанный GitHub-репозиторий. Делать осмысленные коммиты завершённых изменений, проверять результат push. Эта авторизация не означает разрешение на force push, удаление веток или произвольную публикацию.
В отчёте указывать результат, проверку, оставшиеся ограничения и коммит при наличии.

## Делегирование
Использовать минимальное число субагентов только для независимых нетривиальных задач, когда это улучшает скорость или качество. Не делегировать простые локальные изменения.
Давать узкую цель, контекст и ожидаемый результат; исключать пересекающиеся правки. Дальнейшее делегирование — только при обоснованной пользе.
Проверять выводы субагентов, разрешать противоречия самостоятельно и выдавать единый результат. Делегирование не расширяет полномочия.
