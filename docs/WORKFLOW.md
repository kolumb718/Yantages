# Рабочий процесс

## Одна задача
Зафиксировать цель, затрагиваемую область и короткий критерий приёмки. Для небольшого изменения достаточно формулировки в задаче и отчёта; отдельный большой документ не нужен.
Проверить текущее состояние → внести согласованное изменение → проверить → обновить факты → коммит → push.
Не расширять задачу до новой подсистемы без необходимости.

## Git
Новые самостоятельные ветки по умолчанию — codex/<краткое-имя>. Не переключать ветку с чужими незавершёнными изменениями без проверки.
Исторически прототип отправлялся прямо в main. Для дальнейших крупных изменений предлагается ветка и ревью перед объединением; защита main пока не настроена.
Коммит содержит одно понятное изменение и только относящиеся к нему файлы. Перед коммитом проверить diff и git diff --check.
Не использовать git add . при наличии неразобранных файлов. Не отправлять ключи, локальные логи, Library и экспортные архивы.
Не делать force push и не переписывать опубликованную историю по собственной инициативе.

## Документация
STATUS — факты и доказательства проверки; DECISIONS — принятые решения; IDEAS — предложения; ROADMAP — порядок и критерии этапов.
При изменении управления обновлять GAMEPLAY и README Unity. При изменении заказа обновлять STORY и данные интерфейса.
Не копировать одни и те же подробности в каждый файл.

## Ревью
Проверять пользовательский сценарий, потери данных, повторные действия, совместимость движка и ограничения сборки.
Субагент полезен для независимого содержательного ревью или диагностики, но не обязателен для каждой правки.
Внешние публикации проверять по фактическому результату, а не по успешному git push.

## Отчёт
Что изменилось; что именно запускалось; что не проверено; известный блокер; коммит и ссылка, если они существуют.
Не скрывать отсутствие редактора или визуальной проверки словами «готово к игре».
